C++17 · OOP · File-backed commerce

From catalog to confirmed order.

Shopping_Portal is a three-role shopping system written in modern C++. Admins run the catalog and read inventory insights, vendors own their listings, and customers browse, build a cart, keep a wishlist and check out with exact PKR billing and rollback-safe file updates.

What it does

Features at a glance

Every feature below is implemented in the C++ source and exercised by an automated test or a recorded transcript in reports/.

👤

Three role workflows

An abstract Role base class with Admin, Vendor and Customer subclasses. Each overrides registraion() and login() and has its own dashboard.

🛒

Cart, wishlist & history

Matching cart lines merge, quantities can be edited or removed, wishlists persist per user, and every confirmed order is appended to orders.txt.

💰

Exact PKR billing

Prices are stored as integer paisa. Tax and delivery are each 5%, rounded half up, so 2 Apples always cost exactly PKR 330.00.

🛡️

Rollback-safe checkout

Every cart line is validated first. The changed stock files and the new order are staged together and restored from backups if any write fails.

📊

Admin inventory insights New

A read-only dashboard with per-category medians and values, low-stock alerts and a restock cost estimate, built on Analytics.h.

🧾

Quotes with discounts New

catalog_cli --quote "Apples:3,Milk:2" --discount 10 prices a basket, checks stock and applies the discount before tax.

📈

Price statistics New

Min, median, mean and max price for each category, plus restock planning to any target stock level.

📤

CSV & JSON export New

Price-range filters, value sorting, --desc, --limit and spreadsheet-safe CSV output.

🌐

Works offline

This page runs by double-clicking index.html: the catalog and screenshot list are bundled in assets/js/data.js, so no server is required.

How it is built

Architecture, modules & data flow

A shared, standard-library-only domain layer sits under both the Windows console application and the portable audit CLI. The webpage only reads the exported catalog. Nothing in the browser can change the native data files.

Data flow

  1. Seed. data/sample/ holds ItemsCategory.txt (the category index), one file per category (Name - price PKR, quantity), the demo accounts, sample orders and wishlists. It is versioned and never edited by the app.
  2. Runtime copy. run.bat calls tools/prepare_demo.py, which copies the seed into the git-ignored data/runtime/. The portal runs inside that folder, so stock changes, orders and wishlists stay local.
  3. Load and validate. shop::loadCatalog() reads the index, rejects unsafe or duplicate category names, parses each product line and rejects malformed rows, duplicates, bad prices and negative stock.
  4. Transact. At checkout, Cart::validateAndDeductStock() checks every line, builds the new file contents in memory and hands them to shop::commitFiles() together with the new order record.
  5. Audit. catalog_cli loads the same files read-only and prints summaries, statistics, plans, quotes or JSON/CSV.
  6. Evidence. tools/record_evidence.py runs the CLI and the real executable in throw-away copies of the seed, saves the output in reports/ and rebuilds assets/js/data.js. tools/render_figures.py turns those reports into the 30 screenshots.

Object-oriented design

Classes and data structures

The console application uses classic OOP: an abstract base class, three role subclasses and two collaborator classes. The shared library uses plain value types in the shop namespace so it can be tested without any console.

            ┌──────────────────────┐
            │ «abstract» Role      │  reg_name, reg_password, login_name …
            │ + registraion() = 0  │
            │ + login() = 0        │
            └──────────┬───────────┘
        public ┌───────┼────────┐ protected
       ┌───────┴──┐ ┌──┴─────┐ ┌┴──────────┐
       │  Admin   │ │ Vendor │ │ Customer  │──uses──▶ Cart ──reads/writes──▶ category files
       └────┬─────┘ └───┬────┘ └─────┬─────┘           │
            └───────────┴──── uses ──┴──▶ Item         └──▶ shop::commitFiles()
                                   (catalog CRUD, search)

Role abstract

Holds registration and login fields. Declares the pure virtual registraion() and login() and a virtual destructor, so every role is used through the same contract.

Admin : public Role

Only one admin may register (hasRegisteredAdmin()). Menu: users, categories, products, orders & stats, inventory insights, logout. Revenue is summed in paisa.

Vendor : public Role

Stores a company name; vendor_products.txt maps products to vendors so a vendor can only view, add, update or remove its own listings.

Customer : protected Role

Protected inheritance hides the base interface from outside code. Keeps the current user and a 100-slot wishlist, and drives browsing, checkout, history and password change.

Cart

Fixed 500-line arrays of names, prices and quantities. add_item() merges identical name + price lines. validateAndDeductStock() checks every line and commits stock and order together.

Item

Mostly static catalog operations: list, add or remove categories (blocked while products exist), add, update or remove products, and search all categories with de-duplication.

shop::Product, shop::Totals

Plain structs: category, name, price label, price in paisa and quantity; subtotal, tax, delivery and total in paisa. using Cents = std::int64_t.

analytics::PriceStats, Filter, RestockPlan, Quote

Value types returned by the analytics functions. They hold results only, so they are easy to print, test and export.

Design decisions

Integer money

Binary floating point cannot represent 0.10 exactly. Storing paisa in 64-bit integers keeps every bill exact and makes the rounding rule explicit.

Header-only domain layer

Commerce.h and Analytics.h use only the standard library, so the same rules compile into the Windows app, the portable CLI and the unit tests.

Stage, back up, then swap

Text files have no transactions. Writing .shop.tmp files first and keeping .shop.bak copies lets checkout undo a half-finished update.

Read-only analytics

Reports and quotes never write data, so an admin or reviewer can run them at any time without risking stock or orders.

Seed vs runtime data

The versioned seed stays clean. Demos and tests run on copies, so results are repeatable and Git history stays readable.

Reject, don't guess

Ambiguous product names, inverted price ranges, unknown sort keys and overselling all fail with a clear message instead of picking an arbitrary record.

Under the hood

Key algorithms

n = number of products (351 in the sample), k = cart or quote lines.

1. Complete-record parsing

Find the last " - " and the last comma, so names like T-shirts survive. Validate the name, a price with at most two decimals and a 1–9 digit quantity.

dash  = line.rfind(" - ");  comma = line.rfind(',');
if (dash == npos || comma == npos || dash >= comma) reject;
name  = trim(line[0 .. dash]);  price = money(...);  qty = stoi(...)

O(length of line) per record; O(total file size) per catalog.

2. Exact 5% charges

Half-up rounding in integers. Splitting the subtotal into a quotient and remainder of 10,000 avoids overflow for very large bills.

charge = (subtotal / 10000) * bp
       + ((subtotal % 10000) * bp + 5000) / 10000;   // bp = 500 → 5%
total  = subtotal + tax + delivery;

O(1). Tested with 30000 → 1500 and a PKR 10-trillion bill.

3. Rollback-capable commit

Three phases over every changed file: write .shop.tmp; rename the original to .shop.bak and the temp into place; delete backups only after all files succeed. Any exception restores the backups and removes temp files.

O(total bytes written). Pending .tmp/.bak files block a new commit until recovered.

4. Median and mean per category

Group products in a std::map, sort each group by price, take the middle element (or the rounded average of the two middle elements) and the rounded mean.

O(n log n) overall. An "All categories" row is computed the same way.

5. Restock plan

For each product with stock < target: order target − stock units at the catalog price. Lines are sorted by current stock, then name.

O(n log n). Targets outside 1–100,000 are rejected.

6. Quote merging

Each Name:qty item is matched case-insensitively against the catalog. More than one match means ambiguity. Repeated items add to the same line, and the merged quantity is checked against stock.

O(k · n), tiny for real baskets.

7. Deterministic sorting

std::stable_sort by price, stock or value (price × stock), always breaking ties by lower-case name, so reports never change order between runs.

O(n log n).

8. CSV escaping

Fields containing a comma, quote or newline are wrapped in quotes, and inner quotes are doubled, so names like 6" ruler import correctly into Excel.

O(length of field).

Portable C++ audit tool

catalog_cli commands

A read-only command-line tool that validates the same catalog files the portal uses. Run it from the repository root in PowerShell, cmd or the VS Code terminal after building. Each command finishes in well under a second. MinGW builds put it at build\catalog_cli.exe, Visual Studio builds at build\Release\catalog_cli.exe, and Linux/macOS at ./build/catalog_cli.

Explore

# search, filter and sort
.\build\catalog_cli.exe --search oil
.\build\catalog_cli.exe --category Electronics --sort price
.\build\catalog_cli.exe --min-price 1000 --max-price 5000 --sort value --desc --limit 10
.\build\catalog_cli.exe --low-stock --threshold 3 --sort stock
.\build\catalog_cli.exe --categories

Analyse & export

# statistics, planning, quotes, export
.\build\catalog_cli.exe --summary
.\build\catalog_cli.exe --stats
.\build\catalog_cli.exe --restock 8 --category Electronics
.\build\catalog_cli.exe --quote "Apples:3,Milk:2,Bread:1" --discount 10
.\build\catalog_cli.exe --sort value --desc --limit 12 --csv > top.csv

Build · run · test

Setup & commands

Requirements: Windows 10/11, CMake 3.20+, a C++17 compiler (Visual Studio 2022 or MinGW-w64 g++) and Python 3.10+. Run every command from the repository root (the folder that contains CMakeLists.txt) in PowerShell, cmd or the VS Code terminal (Ctrl+`). Python and CMake commands work the same in all three; .\ paths are written for PowerShell and also work in cmd.

Quick start (Windows)

# 1. configure, build and test (one command)
.\build.bat
# 2. reset demo data and start the portal
.\run.bat

Or open Shopping_Portal.sln in Visual Studio and press F5. run.bat builds automatically the first time.

Billing rule

subtotal = Σ unit_price_paisa × quantity   (after discount)
tax      = round_half_up(subtotal × 5%)
delivery = round_half_up(subtotal × 5%)
total    = subtotal + tax + delivery

Known limitations

  • The role UI uses the Windows console API, so it runs on Windows only. The CLI and tests are portable.
  • Passwords are stored in plain text files. This is a learning project, not a production authentication system.
  • Data lives in text files with a single-user design; there is no locking between two running copies.
  • The webpage sandbox is a simulation. It never writes to the native data files.
